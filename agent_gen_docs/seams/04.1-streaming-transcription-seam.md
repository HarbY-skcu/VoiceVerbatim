# Seam: Real-time streaming transcription

Companion to `agent_gen_docs/code-reviews/04.1-realtime-streaming-pipeline.md`.
This doc explains the new seam itself — what it is, why it's shaped this way,
and how it relates to the existing batch (ticket 04) seam — for whoever
implements the real speech-to-text backend or the frontend mic capture next.

## The seam, in one sentence

`StreamingTranscriptionOrchestrator` is the boundary between "audio bytes
arriving over a WebSocket" and "text appearing in the Note," the same role
`TranscriptionPipeline` plays for the batch (Stop/Pause-flush) path — callers
never touch `ActiveNote` directly, they only start/stop a streaming session
and forward chunks.

## Why a second seam, not one seam for both

Batch and streaming have genuinely different contracts:

| | Batch (`TranscriptionService`, ticket 04) | Streaming (`StreamingTranscriptionService`, ticket 04.1) |
|---|---|---|
| Input | one call, whole audio blob | many calls, one chunk each |
| Output | one string | many results: 0+ interim, then 1 final |
| Note write | single atomic `insert_at_cursor` | `insert_streaming`, replace-then-commit |
| Trigger | Stop / Pause (flush) | continuous while `state == "recording"` |

Forcing both through one interface would mean the batch path pretending to
stream a single result, or the streaming path faking a single accumulated
string — either way, hiding a real difference instead of naming it. Two
`Protocol`s in `transcription.py`, two consumers (`TranscriptionPipeline`,
`StreamingTranscriptionOrchestrator`), one shared `ActiveNote`.

## The interim/final reconciliation rule

This is the part that isn't obvious from the endpoint alone, so it's worth
stating precisely. `ActiveNote.insert_streaming(text, *, final)`:

1. **First call of an utterance** (`_pending_span is None`): insert `text`
   at the current cursor. If `final=False`, remember the span `(start,
   start+len(text))` as pending.
2. **Every subsequent call while a span is pending**: delete the pending
   span's current contents, insert the new `text` in its place (a
   *replacement*, not an append — the speech engine revising its guess as
   more audio arrives). Recompute and store the new span if still
   `final=False`.
3. **A call with `final=True`**: do the insert/replace as above, then move
   `cursor` to just past the committed text and clear the pending span.
4. **The next utterance** (after a final) starts a fresh span at the new
   cursor position — it does not reach back and touch already-committed
   text.

This is what lets partial results "self-correct" in place instead of
littering the Note with every intermediate guess, while still landing text
exactly where the user was: "transcription is only added to the place where
the cursor was last; if no place was selected, text is appended at the end,"
per the user's clarification during the grilling.

## Lifecycle: how the orchestrator tracks Recording state

`streaming_orchestrator.start()` / `.stop()` are called from every endpoint
that changes `RecordingSession` state (`start`, `pause`, `resume`, `stop`,
`navigation-stop`), in lockstep with the existing `silence_monitor` and
batch `pipeline` calls:

- **start / resume** → `orchestrator.start()`: opens a new
  `StreamingTranscriptionSession` and spawns a background task that
  consumes `session.results()` into the Note.
- **pause / stop / navigation-stop** → `orchestrator.stop()`: closes the
  session (no forced final — whatever was interim stays interim/committed
  as-is) and waits for the consume task to finish.

The WebSocket endpoint (`/api/recording/stream`) only accepts a connection
while `state == "recording"` (closes immediately with code `4409`
otherwise), and forwards each received frame via
`orchestrator.send_audio(chunk)`.

## The implicit-Pause rule for a dropped socket

If the socket disconnects (client closes it, network drop, anything that
makes `receive_bytes()` raise `WebSocketDisconnect`), `stream_audio`'s
`finally` block calls `_implicit_pause_from_stream_drop()`, which:

1. Closes the streaming orchestrator's session (same as a manual Pause).
2. Calls `recording_session.pause()` — swallowing
   `InvalidRecordingTransition` for the case where the Recording already
   moved on (e.g. a manual Stop raced the disconnect).

This was an explicit design choice confirmed with the user over a
reconnect-and-resume protocol: "If the socket drops mid-recording, treat it
as an implicit pause... I think this seam is quite cleaner." No backoff, no
resume token — the frontend just sees the Recording move to `paused`, the
same state a manual Pause produces, and can offer Resume normally.

## A trap for whoever touches this next: task cancellation across event loops

`StreamingTranscriptionOrchestrator` is a **module-level singleton**
(`main.py`'s `streaming_orchestrator`), shared across the whole app —
including across test modules that each spin up their own `TestClient`
(and therefore their own anyio portal thread/event loop). A background
`asyncio.Task` created on one event loop is a foreign, unusable object on
any other loop: you cannot safely `await`, `cancel()`, or inspect it from a
different thread's loop.

Two consequences baked into this codebase as a result:

- `StreamingTranscriptionOrchestrator.reset()` exists **only** for test
  teardown — it drops task/session references without awaiting or
  cancelling anything, because by the time a later test's setup runs, the
  task's own loop may already be gone.
- `backend/tests/conftest.py` forces `test_recording_stream_ws.py` (the
  only module that actually opens real WebSocket connections) to run
  **last** in the suite, so any lingering portal-thread state from it can't
  leak into other modules' plain-HTTP tests against the same singletons.

If you add another module that opens real WebSocket connections via
`TestClient`, either give it the same `streaming_orchestrator.reset()`
pattern in `setup_function`, or extend the conftest ordering rule.

## Where the next tickets plug in

- **Frontend mic capture** (`getUserMedia`/`AudioWorklet`) needs to open
  `ws://.../api/recording/stream` and send raw chunks — the backend side
  of that contract is fully tested and stable now.
- **A real `StreamingTranscriptionService`** implementation replaces
  `UnconfiguredStreamingTranscriptionSession` in `main.py` (same pattern as
  the batch `UnconfiguredTranscriptionService` from ticket 04) — it only
  needs to satisfy `send_audio` / `results` / `close`; nothing else in the
  system needs to change.
- **Reconnect-with-resume**, if ever wanted, would replace the
  implicit-Pause call in `_implicit_pause_from_stream_drop` with logic that
  distinguishes "client meant to disconnect" from "network blip" — out of
  scope today by explicit user decision.
