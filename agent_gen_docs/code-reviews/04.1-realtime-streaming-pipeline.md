# Code Review: 04.1 — Real-time streaming audio capture & transcription pipeline

## Scope agreed with the user (via `/skill:grill-me`)

- Land the **full** end-to-end path: mic capture is out of scope for this
  pass at the frontend UI level (no `getUserMedia`/`MediaRecorder` wiring
  yet), but the **backend streaming seam** is landed completely — a
  WebSocket ingest endpoint, a streaming transcription service contract,
  and Note reconciliation for interim/final results — so that a real mic
  producer can be plugged in without further backend changes.
- `/api/recording/stream` (WebSocket) replaces `/api/recording/audio-chunk`
  (POST) as the ingest seam for streaming clients. The old POST endpoint is
  kept for the batch path (ticket 04) but documented as legacy.
- Interim results **replace** a pending span anchored at the cursor at the
  moment streaming starts; a final result commits that span and moves the
  cursor past it. Cursor repositioning is only meaningful during
  pause/idle/stop, matching the user's clarification that transcription
  always targets "wherever the cursor was last, or the end if unset."
- The stream only accepts frames while `RecordingSession.state ==
  "recording"`.
- A dropped/closed socket is treated as an **implicit Pause** — same
  seam as a manual Pause, chosen by the user as the cleaner mental model
  over an explicit reconnect protocol.

## What shipped

1. **`ActiveNote.insert_streaming(text, *, final)`** (`backend/app/note.py`)
   — new method alongside the existing atomic `insert_at_cursor`. Tracks a
   `_pending_span` `(start, end)` so repeated interim calls replace prior
   interim text instead of appending beside it; `final=True` commits and
   clears the span.
2. **`StreamingResult` / `StreamingTranscriptionSession` /
   `StreamingTranscriptionService`** (`backend/app/transcription.py`) — the
   streaming counterpart to the existing batch `TranscriptionService`
   `Protocol`. A session accepts audio chunks and exposes an async
   iterator of results (interim, then one final); `close()` ends the
   session without forcing a final, which is what the implicit-Pause path
   relies on.
3. **`StreamingTranscriptionOrchestrator`**
   (`backend/app/streaming_orchestrator.py`) — the seam every caller
   (HTTP layer, tests) goes through: `start()` opens a session and spawns
   a background task consuming its results into the Note via
   `insert_streaming`; `send_audio()` forwards chunks; `stop()` closes the
   session and waits for the consume task to finish. Mirrors
   `TranscriptionPipeline`'s role for the batch path.
4. **`/api/recording/stream` WebSocket endpoint** (`backend/app/main.py`)
   — accepts frames only while `state == "recording"` (closes with code
   `4409` otherwise), forwards each frame to the orchestrator, and on
   `WebSocketDisconnect` (or any exit from the receive loop) invokes
   `_implicit_pause_from_stream_drop()`, which closes the streaming
   session and pauses the Recording exactly like the `/pause` endpoint.
5. Wired `streaming_orchestrator.start()`/`.stop()` alongside the existing
   `pipeline`/`silence_monitor` calls in `start`, `pause`, `resume`,
   `stop`, and `navigation-stop` so the streaming session's lifecycle
   tracks the Recording lifecycle exactly.
6. Resolved the `feature-4`/`HEAD` merge conflict in `main.py` (silence
   timeout monitor + ticket-04 transcription pipeline now coexist), which
   this ticket depended on.

## Notable issue found and fixed during implementation: an infinite-loop hang

An intermediate version of the WebSocket `finally` cleanup retried on
`CancelledError`:

```python
while True:
    try:
        await _implicit_pause_from_stream_drop()
        break
    except asyncio.CancelledError:
        continue
```

Once an `asyncio.Task` is cancelled, **every subsequent `await` inside that
task re-raises `CancelledError`** until the cancellation is allowed to
actually propagate out. TestClient's WebSocket teardown cancels the
connection handler's task, so this loop caught the cancellation and looped
straight into another `await` that was cancelled again — infinitely, doing
no real work — hanging the test process for 7+ minutes before the harness
aborted it. Fixed by making the cleanup a **direct, single `await`** (no
retry) and documenting in `main.py` that TestClient's forced task
cancellation is a harness limitation, not production behaviour: a real
client disconnect makes `receive_bytes()` raise `WebSocketDisconnect`
normally and the `finally` block runs to completion. See
`agent_gen_docs/README.md` cross-reference / the seam doc in this same
directory for the full write-up of that failure mode.

## Known limitations / follow-ups (explicitly out of scope here)

- No frontend mic capture (`getUserMedia`/`AudioWorklet`) yet — the
  WebSocket ingest exists and is tested, but nothing sends real audio into
  it yet.
- No real `StreamingTranscriptionService` implementation — `main.py` wires
  an `UnconfiguredStreamingTranscriptionService` placeholder, matching the
  pattern already established for the batch path in ticket 04.
- No reconnect protocol — a dropped socket pauses rather than resuming;
  the user confirmed this is the desired seam for now, not a gap.
- `TestClient`'s anyio-portal WebSocket teardown has real quirks (detailed
  in `test_recording_stream_ws.py` and the seam doc) that required
  ordering `test_recording_stream_ws.py` last in the suite
  (`backend/tests/conftest.py`) to avoid state leakage across test
  modules sharing the app's singletons.
