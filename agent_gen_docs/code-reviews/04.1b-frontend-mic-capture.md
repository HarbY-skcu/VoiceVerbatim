# Code Review: 04.1 (cont'd) — Frontend mic capture wired to the streaming ingest

Companion to `agent_gen_docs/code-reviews/04.1-realtime-streaming-pipeline.md`
and `agent_gen_docs/seams/04.1-streaming-transcription-seam.md`, which landed
the backend streaming seam but explicitly left mic capture out of scope
("nothing sends real audio into it yet"). This closes that gap.

## What shipped

1. **`MicWebSocketStreamer`** (`frontend/src/mic-stream.ts`) — opens
   `getUserMedia`, waits for a WebSocket to `/api/recording/stream` to
   open, then starts a `MediaRecorder` (250ms timeslice) whose
   `ondataavailable` chunks are forwarded over the socket while it's open.
   `stop()` halts the recorder, stops every mic track, and closes the
   socket. Every browser capability (`getUserMedia`, `MediaRecorder`,
   `WebSocket`) is behind an injectable `MicWebSocketStreamerDeps` seam —
   the same pattern `AudioSourceSelector` uses for `enumerateDevices` — so
   this is unit-tested (8 tests) without real hardware or a network.
   `createBrowserMicStreamer()` is the production factory wiring real
   browser APIs.
2. **`RecordingControls` wiring** — takes an optional `MicStreamer`
   collaborator; after any successful transition it starts the streamer
   when the resulting state is `"recording"` and stops it otherwise. Driven
   by resulting state, not action name, so Record/Resume and Pause/Stop
   are each handled by one branch. A rejected transition (409) never
   touches the mic streamer — the backend didn't commit anything. Mic
   failures (denied permission, unplugged device) are caught and logged
   rather than left uncaught, since by the time `syncMicStreamer` runs the
   Recording state transition has already been committed by the backend;
   surfacing mic failure as an uncaught exception would leave the UI stuck
   mid-render for a problem the backend already moved past.
3. **`renderer.ts`** — constructs `createBrowserMicStreamer` with a
   `deviceIdProvider` reading `AudioSourceSelector.activeDeviceId`, so
   whichever Audio Source the user picked before hitting Record/Resume is
   the device requested from `getUserMedia`. This is a one-way read, not a
   new coupling between the two components' internals.

## Testing

TDD throughout: `mic-stream.test.ts` (8 tests, fake `WebSocket`/
`MediaRecorder`/`getUserMedia`) covers acquire-then-open-then-record
ordering, chunk forwarding (including dropping empty chunks), stop
cleanup, start idempotency, and device-id passthrough. `recording-controls.test.ts`
gained 5 tests covering streamer start/stop on each of the four
transitions plus the rejected-transition no-op case. Full suites: 34
frontend tests, 45 backend tests, all passing.

## A timing note for whoever touches `mic-stream.ts` next

The initial version of `start()` waited purely on the socket's `onopen`
callback firing. Because `getUserMedia` resolves asynchronously, a fake
(or, in principle, a fast real) socket can already be `readyState ===
OPEN` by the time `onopen` is attached — and an already-fired event never
fires again. Fixed by also checking `readyState` immediately after
attaching the handler and resolving synchronously if it's already open.

## Known limitations / follow-ups (still out of scope)

- No real `StreamingTranscriptionService` backend implementation — this
  ticket is the producer side only; `main.py` still wires
  `UnconfiguredStreamingTranscriptionService`, unchanged by this work.
- No UI feedback for mic permission denial beyond a console log — the
  Record button will appear to have started (backend state moved to
  `"recording"`) while no audio actually streams. A visible error surface
  for this is a reasonable next increment but wasn't part of this ticket's
  agreed scope.
- `MediaRecorder`'s emitted chunk format (defaults to the browser's
  preferred codec, typically WebM/Opus) is not yet negotiated with or
  validated against whatever a real `StreamingTranscriptionService` will
  expect — that contract needs to be settled when the real backend service
  is implemented.
